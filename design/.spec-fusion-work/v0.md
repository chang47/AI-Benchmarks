# Task 22 — "Broken Tabletop" (slugs 22a fix-it / 22b grow-it) — spec v0 (orchestrator draft)

## 0. Feature name and purpose
**Lantern** (working name): a self-hosted, offline, 5E-compatible web virtual tabletop that a real group can run for a session. The GM runs one Node server and shares one link over Tailscale. The app is built correct first and proven correct by a large hidden test suite. Then **11 realistic bugs** are planted in it: 5 reported as vague player complaints and 6 unreported. That buggy build is **22a**, which tests diagnosing and fixing bugs inside a ~20k-line codebase the agent didn't write. The clean app is **22b**, which tests product sense: "brainstorm what it needs next, then build it." Every planted bug is a mistake a real developer would make. Each can be shown by hand in two browser windows in under a minute, and each is caught by a deterministic hidden fail→pass test.

---

## 1. Explicit assumptions and decisions (read first; the adversarial panel should attack these)
- **A1 Names.** The app is called "Lantern". The demo fixture uses our own character names (Mira, Brother Aldric) and neutral player names (Sam, Jo, Priya). Nothing is taken from non-SRD settings.
- **A2 Rendering.** The map is rendered with **DOM/SVG elements, not a canvas library**. Tokens, fog cells and rulers are real elements carrying stable identifying attributes, so browser tests can read positions without pixel probing and we avoid a heavy dependency. At session scale (≤ 50 tokens, ≤ 60×60 cells) the performance cost is acceptable. *Weak spot: judges may find it looks less slick than a canvas VTT. Mitigated by styling.*
- **A3 Identity lives in the URL fragment of each window**, not in shared browser storage. The GM link and each player's personal rejoin link carry their key. This lets two windows in one browser act as GM and player (needed for the camera and the grader), and a refresh keeps each window's identity (needed for bug B06's repro).
- **A4 All dice are rolled on the server.** A seeded generator runs per game, and a documented **test mode** (off by default) can set the seed and queue forced die faces. No on-camera repro needs forced dice. Only the hidden tests use them.
- **A5 Grading surface.** Hidden tests use only (a) the documented wire protocol, (b) documented test-mode setup hooks (reset, load fixture, seed, forced faces), and (c) the rendered UI through roles, labels and a small documented set of test ids. They **never import internal modules**. This keeps any valid fix passing.
- **A6 Where each bug is graded.**
  - Security and visibility bugs (a player could cheat or see secrets) are graded **at the protocol level**, so the server must enforce the fix; a client-only patch does not count.
  - Non-security bugs whose fix could legitimately live on either side are graded **through the UI**, so a fix on either side counts.
- **A7 Rules edition.** SRD 5.2.1 (2024 rules), CC-BY-4.0 only. Rules whose exact 5.2.1 wording the council hasn't verified are marked **[verify]**, and their tests must avoid the unverified edge until checked against the PDF.
- **A8** Unreported bugs are not listed anywhere in the shipped 22a repo, prompt, or visible tests. The spec, the clean source and the patches do live in the public bench repo (accepted per clarification 9).

## 2. The correct app — acceptance criteria (EARS)

### 2.1 Games, identity, connectivity
- **APP-01** When the GM creates a game from the landing page, the system shall create a game with a secret GM key (≥128-bit, from a cryptographic source independent of the dice seed) and a separate player invite link. *Why: anyone reachable over Tailscale Funnel could otherwise take over the table, and seeding dice for tests must never make keys predictable.*
- **APP-02** When a person opens the invite link and enters a display name, the system shall admit them as a player and give them a personal rejoin link. They may then claim one unclaimed character or stay a spectator. *Why: friends should need nothing but a link.*
- **APP-03** While a window has joined a game, the system shall keep that window's identity in its own URL fragment, so two windows in one browser can be different participants and a refresh keeps identity (A3).
- **APP-04** When the connection drops, the client shall show a visible "Reconnecting…" state, reconnect automatically, and resynchronize the full viewer-appropriate state. *Why: wifi blips happen mid-session. Resync is also a deliberate bug site (B06).*
- **APP-05** The system shall show a presence list with every participant, their role, and whether they are online.
- **APP-06** The server shall serve the built client, the HTTP API and the WebSocket on **one configurable port**, same-origin, with relative URLs and automatic ws/wss selection. *Why: a single `tailscale serve`/`funnel` mapping must be enough; HTTPS termination by Tailscale must just work.*
- **APP-07** The README shall document hosting for a real group: run the server, share it with `tailscale serve` (tailnet friends) or `tailscale funnel` (anyone with the link), and what Funnel exposure means for the GM key. At runtime the app shall make no network calls beyond its own origin.

### 2.2 Authority, permissions, visibility (the security spine)
- **APP-10** The server shall be authoritative. Every state change is a command the server validates (shape, role, ownership) before applying and broadcasting; the server rejects invalid commands with an error that only the sender sees. *Why: players may run modified clients; the README says so.*
- **APP-11** When a player sends a command that targets a token or character they don't own (move, nudge, HP change, sheet edit, condition change), the server shall reject it. The GM may act on everything.
- **APP-12** The server shall build every outbound message **per viewer**. A player never receives, by any message type (snapshot, update, drag stream, chat, history, roll, tracker), the following:
  - hidden tokens;
  - tokens entirely under fog, except player-owned tokens, which are always visible to all players;
  - GM-only rolls and whispers addressed to others;
  - monster AC and HP numbers;
  - GM notes.
  *Why: this is what makes a VTT trustworthy. It is also the main bug site for information leaks.*
- **APP-13** While a monster token is visible to a player, the player shall see its name and a coarse health state (Healthy / Bloodied at ≤ half HP / Down), never exact HP.

### 2.3 Scenes, maps, grid
- **APP-20** When the GM uploads a map image (PNG/JPEG/WebP, ≤ 20 MB) to a scene, the server shall store it locally under the data directory and serve it to viewers of that scene. *Why: offline; a group's own maps.*
- **APP-21** The GM shall be able to set grid cell size (pixels) and grid offset, and toggle the grid overlay. The map's size in cells follows from the image.
- **APP-22** The GM shall be able to create, rename, duplicate and delete scenes, and preview any scene without moving players.
- **APP-23** When the GM activates a scene, the system shall move every player's view to that scene and show **only** that scene's map, fog and tokens. *Why: "pull players to the forest"; deliberate lifecycle bug site (B08).*
- **APP-24** Every participant shall be able to pan (drag the background or use the space-drag) and zoom (wheel toward the cursor, plus on-screen +/− and "fit"), between 25% and 400%. Pan and zoom are per window and never broadcast.
- **APP-25** The app shall ship two original, freely licensed sample maps made for the project (the tavern and the forest road used by the fixture) as vector art with a declared license.

### 2.4 Tokens and movement
- **APP-30** The GM shall be able to place tokens for characters, SRD monsters, or plain markers. Each token has a name label, an image or a coloured initial disc, a size footprint (Tiny/Small/Medium = 1 cell, Large = 2×2, Huge = 3×3, Gargantuan = 4×4), and an optional owner.
- **APP-31** When a permitted participant drags a token and releases it, the system shall snap the token to the grid cell under the pointer (the footprint's top-left cell for multi-cell tokens) at **any zoom and pan**. It shall show a live distance readout in feet during the drag. *Why: the most-used interaction; coordinate transforms are a deliberate bug site (B04).*
- **APP-32** While a token is being dragged, the system shall stream its live position (≤ 20 updates per second) to other viewers who are allowed to see that token, so the group sees movement as it happens. *Deliberate bug site (B01).*
- **APP-33** When a permitted participant presses an arrow key with a token selected, the system shall move the token one cell in that direction, clamped to the map. Any participant may select any visible token to inspect it, but only permitted participants may move it. *Deliberate bug site (B02).*
- **APP-34** The GM shall be able to toggle a token hidden. Hidden tokens are shown to the GM at reduced opacity with a hidden marker and are never sent to players (APP-12).
- **APP-35** Each token shall show an HP bar (full numbers to the GM and the owner, coarse state to others per APP-13) and condition badges.

### 2.5 Fog of war (manual, cell-based)
- **APP-40** While fog is enabled for a scene (off by default; enabling covers the whole map), players shall see fogged cells as opaque. The GM sees them as translucent dark.
- **APP-41** When the GM drags a Reveal or Hide rectangle, the system shall reveal or hide **every cell the rectangle covers, including the cells under both corners**, exactly as the GM's preview showed. The protocol documents rectangles as inclusive corner cells. *Deliberate bug site (B11).*
- **APP-42** When cells are revealed, tokens in them that are now visible shall appear for players without a refresh. When cells are hidden again, non-player tokens in them shall disappear for players.

### 2.6 Measurement
- **APP-45** Every participant shall have a ruler tool that measures cell-to-cell distance in feet. Each square is 5 ft and diagonal steps count as 5 ft **[verify against SRD 5.2.1 grid rule]**. The ruler is local to the window and must be correct at every zoom and pan.

### 2.7 Dice and chat
- **APP-50** When a participant sends `/r <expression>` (or `/roll`), the server shall roll it and post a roll card showing the expression, each die, the kept/dropped dice, and the total. Supported notation:
  - `NdM`, and `dM` with an implied count of 1;
  - `d%`;
  - keep/drop highest/lowest (`kh`, `kl`, `dh`, `dl`);
  - several dice groups and constants joined by `+` and `−`.
  
  Limits are 1–100 dice per group and 2–1000 sides. *Why: the core social loop. The implied count is a deliberate bug site (B10).*
- **APP-51** If an expression is invalid or out of limits, then the system shall show a readable error to the sender only and post nothing.
- **APP-52** When a participant sends `/gmr <expression>`, the result shall be visible only to the GM and the roller.
- **APP-53** When a participant sends `/w <name> <text>`, the message shall be delivered only to the named participant(s) and the GM, **both live and in any history replay** (join, reconnect, refresh). *Deliberate bug site (B06).*
- **APP-54** The system shall keep and persist the last 500 chat entries per game and replay them, filtered per viewer (APP-12), on join and reconnect.
- **APP-55** Roll cards shall highlight a natural 20 and a natural 1 on a d20 and show why advantage or disadvantage applied (for example, "Disadvantage: Poisoned"). *Why: camera readability, and it makes rules visible to players.*

### 2.8 Characters and sheets (single-class, levels 1–20)
- **APP-60** A character sheet shall hold the following, each editable by the owner and the GM only:
  - name, class and level;
  - six ability scores;
  - saving-throw and skill proficiencies, with expertise;
  - AC, max HP, current HP and temp HP;
  - speed, hit dice, conditions, exhaustion level, death saves;
  - attacks (name, ability, proficient flag, bonus, damage dice and type);
  - prepared spells from the compendium;
  - freeform features/inventory text;
  - damage resistances, vulnerabilities and immunities.
- **APP-61** The sheet shall derive the following and never let them be typed in:
  - ability modifiers: floor((score − 10) / 2);
  - proficiency bonus: 2 + floor((level − 1) / 4);
  - skill and save modifiers (proficiency ×1, expertise ×2);
  - passive Perception;
  - initiative modifier;
  - spell save DC and spell attack bonus;
  - spell slots per class and level (full, half 2024 table, warlock Pact Magic per the SRD research tables);
  - cantrip damage scaling at levels 5, 11 and 17.
- **APP-62** When the owner or GM clicks a check, save, skill, attack, damage, initiative or spell, the system shall roll it on the server with the correct modifier and post a roll card. Attacks against a targeted token report HIT/MISS; players see only HIT/MISS, the GM also sees the AC.
- **APP-63** When an attack roll is a natural 20, it shall hit and be a critical hit (damage dice rolled twice, modifiers once). A natural 1 shall miss regardless of the total. *These are "trap" rules the tests pin down.*
- **APP-64** While the roller has any of the conditions below, the system shall apply that condition's effect to the roller's **own** d20 rolls automatically. Target-side effects are backlog. Advantage and disadvantage cancel to a straight roll no matter how many sources of each apply.

  | Condition | Effect on the roller's own d20 rolls |
  |---|---|
  | Poisoned | Disadvantage on attack rolls and ability checks |
  | Blinded | Disadvantage on attack rolls |
  | Prone | Disadvantage on attack rolls |
  | Restrained | Disadvantage on attack rolls and Dex saves |
  | Frightened | Disadvantage on attack rolls and ability checks (simplified: the source is assumed to be in sight) |
  | Invisible | Advantage on attack rolls |
  | Exhaustion | −2 × level on every d20 test (2024) |
  | Paralyzed, Stunned, Petrified, Unconscious | Automatic failure on Str and Dex saves |
- **APP-65** Casting a prepared leveled spell shall spend a slot of the chosen level (≥ the spell's level) and refuse if none remain. Casting a concentration spell shall end any previous concentration and mark the caster as concentrating.

### 2.9 Monsters and compendium
- **APP-70** The GM shall be able to browse and search a vendored SRD 5.2.1 subset and add creatures to the scene: about 25 monsters, CR 0–10, several types, some with multiattack, resistances and condition immunities. Each added monster is an independent instance with its own HP, set to the stat block average.
- **APP-71** The GM shall be able to roll a monster's initiative, saves, checks, attacks and damage from its stat block. These rolls are GM-only by default, with a per-game toggle to make them public.
- **APP-72** Players shall be able to browse the spells and conditions compendium (reference use during play).

### 2.10 Damage, healing, conditions, death
- **APP-80** When damage of a given type is applied to a creature, the system shall apply it in this order:
  1. Immunity → 0.
  2. Resistance → half, rounded down.
  3. Vulnerability → double. **[verify 5.2.1 ordering wording]**
  4. Temporary HP absorbs damage before HP.
  5. HP is floored at 0.
  
  The system shall show the arithmetic to the GM. *Trap rule: rounding down.*
- **APP-81** When a PC drops to 0 HP, the system shall make it Unconscious and start death saves. If the damage left over after reaching 0 is at least its HP maximum, the PC dies instead. A monster at 0 HP is marked Down (defeated overlay) and stays on the tracker until removed.
- **APP-82** When a PC at 0 HP takes damage, the system shall record one death-save failure, or two if the damage came from a critical hit. If that damage equals or exceeds the PC's HP maximum, the PC dies.
- **APP-83** When a death save is rolled, the result shall be applied as follows:
  - 10 or higher: a success.
  - Below 10: a failure.
  - Natural 1: two failures.
  - Natural 20: the PC regains 1 HP and becomes conscious.
  - Three successes: Stable.
  - Three failures: Dead.
  
  The owner or GM may also set the death-save marks by clicking them (table correction).
- **APP-84** When a creature regains HP by any route (heal dialog, HP quick-edit, spell, rest, natural 20 death save), the system shall cap HP at the maximum. If the creature was at 0 HP, the system shall also remove Unconscious and **reset death saves and Stable**. *Two deliberate bug sites (B05 quick-edit path, B09 death-save reset).*
- **APP-85** When a creature gains temporary HP while it already has some, it shall keep the higher value; temporary HP do not stack.
- **APP-86** The GM and owner shall have an HP quick-edit on the token: a signed number applies damage (negative) or healing (positive) through the same rules as APP-80 and APP-84. Plain untyped damage ignores resistances.
- **APP-87** When a concentrating creature takes damage, the system shall prompt a Constitution save with DC = max(10, floor(damage / 2)), capped at 30. On failure it shall end concentration. If the creature becomes Incapacitated (or any condition that includes it), concentration shall end.
- **APP-88** The GM and owner shall be able to add and remove any of the 15 SRD conditions and set exhaustion 0–6. Exhaustion 6 means death.

### 2.11 Combat tracker
- **APP-90** When the GM starts combat and adds tokens, the system shall show every participant a tracker ordered by initiative, highest first, with a visible current-turn highlight and a round counter starting at round 1. Hidden combatants are omitted from players' trackers. While a hidden combatant is current, players see "GM's turn".
- **APP-91** Initiative values shall come from one of three sources, and all three shall **order numerically**:
  - a server roll (click "roll initiative" for selected, or "roll for all monsters");
  - an owner roll from the sheet;
  - a number the GM types in (for groups rolling physical dice).
  
  Ties are ordered by higher initiative modifier, then name (a documented house choice, not a rule). The GM may also drag to reorder. *Typed input is a deliberate bug site (B07).*
- **APP-92** When the GM presses Next, the highlight shall move to the next combatant. Wrapping past the end increments the round.
- **APP-93** When a combatant is removed, the current creature shall stay current (if a different combatant was removed) or the turn shall pass to the next creature in order (if the current one was removed). No one's turn may be skipped or granted twice. *Deliberate bug site (B03).*
- **APP-94** When the GM ends combat, the system shall clear the tracker. A new combat starts at round 1.

### 2.12 Rests and resources
- **APP-100** When a Short Rest is taken for a character, the owner or GM may spend hit dice, each healing die + CON modifier (minimum 1 per die **[verify]**). Warlock Pact slots recover.
- **APP-101** When a Long Rest is taken, the system shall do all of the following:
  - restore HP to max and all hit dice (2024);
  - restore all spell slots;
  - remove one exhaustion level;
  - clear temp HP **[verify]**, death saves and concentration.

### 2.13 Persistence
- **APP-110** The server shall autosave each game to its data directory within 2 s of a change, using atomic writes, and restore everything after a restart: scenes, tokens, fog, sheets, tracker, chat history.
- **APP-111** The GM shall be able to export a game to a single JSON file and import it as a new game. Exports include uploaded map images.

### 2.14 Content, licensing, branding
- **APP-120** The app shall contain the verbatim SRD 5.2.1 attribution sentence in the README, a `data/LICENSE-SRD.md`, and an in-app About panel. It shall describe itself only as "5E-compatible".
- **APP-121** The repository shall contain none of the product-identity terms listed in the SRD research note: brand names, setting names, the proper-named spells/creatures, and the stray non-SRD names. A visible test scans UI strings and data for them. Vendored data drops image and url fields.
- **APP-122** Game data shall be a small, normalized, hand-checked subset: about 25 monsters, about 35 spells (mostly cantrips to 3rd level, mixing attack, save, concentration and ritual), the core data for all 12 classes (hit die, save proficiencies, casting type), 15 conditions, 18 skills, and about 40 weapons and armor. Rules tables are hand-written and checked against the PDF.

### 2.15 Determinism and test mode
- **APP-130** While the server is started with test mode enabled (environment flag; off by default; refuses to start in test mode unless bound to loopback), it shall expose documented setup hooks:
  - reset all state;
  - load a named fixture (with fixed participant keys);
  - set the dice seed for a game;
  - queue forced die faces.
  
  Test mode shall change no game rule. *Why: deterministic tests and a one-click "reset demo" for the camera.*
- **APP-131** With the same seed and the same command sequence, the server shall produce the same dice results.
- **APP-132** The repo shall include a `demo` launcher that starts the server in test mode, loads the "Sunken Tavern" fixture and prints the GM link and each player link. It shall also be able to start a second instance on another port (for side-by-side before/after).

### 2.16 Codebase shape (it must feel like a real project)
- **APP-140** The repository shall be one npm-workspaces monorepo with three packages:
  - `shared`: rules engine, dice, protocol types, validators, data;
  - `server`: Node + TypeScript, WebSocket, persistence, projection;
  - `client`: Vite + React + TypeScript.
  
  One root check command shall run typecheck, lint, visible unit tests and visible e2e smoke.
- **APP-141** The shipped repo shall include a README (features, run, host), `docs/PROTOCOL.md` (every message and command shape, rectangle conventions, visibility contract), `docs/TESTING.md` (test mode, fixture, documented test ids) and `docs/RULES.md` (which SRD rules are implemented and the simplifications).
- **APP-142** The codebase shall measure 15–25k non-blank lines, counted over TS/TSX/CSS and all tests, excluding data JSON and the lockfile. Target split:

  | Area | Approx. lines |
  |---|---|
  | shared | 3k |
  | server | 3.5k |
  | client | 8k |
  | visible tests | 1.5k |
  | hidden tests | 4k |
  
  The 11 bug sites shall be spread across ≥ 9 distinct files in all three packages.
- **APP-143** The visible test suite shall be modest and realistic: about 50 unit/integration tests plus 2 browser smoke tests. It shall pass on the clean app **and** on the fully bugged app, and shall not exercise any planted bug's failing path.

## 4. How the design deliberately creates good bug sites
Each core feature is built so that realistic mistakes have somewhere natural to happen:
- **Parallel paths to the same invariant.** Features added later can each forget a rule the original path enforces:
  - drag vs keyboard nudge (ownership);
  - heal dialog vs HP quick-edit (clamping);
  - live chat vs history replay (whisper filtering);
  - full update vs live drag stream (visibility).
- **Per-viewer projection on the server.** Every new outbound message type has to go through the projector. Forgetting to is the classic information leak, and a player can see it on camera.
- **Ordered list plus a cursor.** The initiative tracker stores a list and a current index; changing the list without fixing up the index skips turns.
- **Coordinate transforms.** Screen ↔ map conversion with zoom, pan and grid offset. A conversion site missed when zoom-to-cursor was added misplaces drops only when zoom ≠ 100%.
- **Client cache vs server truth.** A handler that merges into the local cache where it should replace it leaves ghost state.
- **Typed values crossing the wire.** Numbers that arrive as text from an input sort as text.
- **Boundary conventions between packages.** An inclusive rectangle in the protocol meets an exclusive loop on the server.
- **Rules state added after the rules that must reset it.** Death saves were added after healing was written.
- **Parser rewrites.** Adding keep-highest drops the old implied-count default.

## 5. Planted-bug catalog

### 5.1 Catalog-level acceptance criteria
- **CAT-01** Each planted bug shall be a stored patch against the clean app. Each patch reads like ordinary product code:
  - no comment, TODO, name, log line or test mentions the bug;
  - any clean-code comment that would contradict the bug is adjusted too;
  - diff size ≤ 40 changed lines;
  - the patch may span several files.
- **CAT-02** Each bug shall have ≥ 1 hidden fail→pass (F2P) test that is:
  - red when the bug is applied alone and red with all 11 applied;
  - green on the clean app;
  - stable 3 out of 3 runs.
- **CAT-03** Each bug shall have a small **local sentinel set**: pass→pass tests of the neighbouring behaviour that a delete-the-feature "fix" would break. For reported bugs, these gate the points.
- **CAT-04** Each bug shall be validated against **2–3 alternative correct fixes**. Each alternative must pass the bug's F2P tests, its local sentinels and every regression group. *Why: prevents tests that are too narrow.*
- **CAT-05** No bug shall crash the app on load, fail the build, or break any feature beyond its own symptom. With all 11 bugs applied, every regression (P2P) group shall stay green.
- **CAT-06** Each bug shall have an on-camera repro. It starts from "reset demo", takes ≤ 60 s by hand in a real browser with at most two windows (GM + Sam), and ends in an outcome a non-coder can see is wrong. The same script on the fixed build shows the correct outcome. The whole repro set shall take ≤ 10 min.
- **CAT-07** The hidden tests' inputs shall differ from the complaint examples: different creatures, numbers and cells.

### 5.4 Bug entries

#### B01 — Live drag stream leaks hidden and fogged tokens (REPORTED · Hard · info leak, multi-file)
- **How it got there:**
  - Live movement (APP-32) was added after the projection layer existed.
  - To keep drag smooth, the new handler relays "token is being dragged" events straight to everyone else in the room. It skips the per-viewer projector because the event "only carries a position".
  - The event also carries the token's display basics (name, image, size), so that clients with stale state can draw the moving token.
  - On the client, the drag layer draws a moving copy for any token id in the stream, including ids it has never seen.
  - The final "token updated" on release still goes through the projector, so the token vanishes again when the drag ends.
- **On-camera repro (≈ 30 s):**
  - Setup: reset demo, then put the GM window and Sam's window side by side. Sam sees an empty dark cellar.
  - Action: the GM slowly drags a hidden goblin across the cellar and into the common room.
  - **Before:** in Sam's window a goblin with its name label glides across the map, then disappears when the GM lets go.
  - **After:** nothing appears in Sam's window at any point. Once the GM un-hides the goblin, it appears at its final position.
- **Complaint (Sam):** "Kind of spoiled last session — I could see the goblins before our GM revealed them. Not the whole time, they just kind of showed up for a bit during the fight?"
- **Detecting tests:** a protocol test with the GM, a player, and a sniffing player socket.
  - F2P-1: the GM streams a drag of a hidden token → the player socket receives no message that contains the token's id or name.
  - F2P-2: the GM drags a non-hidden monster that stays entirely inside fogged cells → no message reaches the player.
- **Local sentinels (gate):**
  - A drag of a visible token is streamed to players.
  - A hidden token's drag is streamed to the GM.
  - Un-hiding delivers the token to players at its current cell.
  - A player-owned token under fog is streamed to its owner.
- **Alternative fixes to validate:**
  - Route the drag event through the projector.
  - Filter recipients with the visibility predicate before the relay.
  - Drop drag streaming for tokens that aren't visible to that recipient, computed per recipient.
  - A client-only "ignore unknown ids" fix **fails**, by design (A6).

#### B02 — Keyboard nudge skips the ownership check (REPORTED · Medium · permission, feature-add)
- **How it got there:**
  - Arrow-key nudging (APP-33) was added later as its own command, separate from drag-move, because it moves by one cell.
  - The server handler checks that the token exists and clamps the move to the map, but it never calls the ownership guard that the move handler uses.
  - On the client, the keyboard handler acts on whatever token is *selected*. Any player may select any visible token to inspect it, and only the drag handler checks ownership.
- **On-camera repro (≈ 20 s):**
  - Action: in Sam's window, click Brother Aldric (Jo's token) to select it, then press → three times.
  - **Before:** Aldric walks three squares in both windows.
  - **After:** Aldric stays where he is in the GM window. Sam's window may show a brief refusal or snap back.
- **Complaint (Jo):** "Pretty sure someone else in our group can move my character. I left my cleric by the bar and next thing I know he's across the room. Nobody's owning up to it 😅"
- **Detecting tests:**
  - F2P-1: a raw player socket sends a nudge for a token that player doesn't own → the server rejects it and the token's cell is unchanged for the GM.
  - F2P-2: the same attempt on a hidden monster is rejected, and the rejection reveals nothing about the hidden token.
- **Local sentinels (gate):**
  - The owner can nudge their own token.
  - The GM can nudge any token, including hidden ones.
  - The owner's drag-move still works.
  - Nudging clamps at the map edge.
- **Alternative fixes:**
  - Guard inside the nudge handler.
  - A central permission check applied to all token commands.
  - Implementing nudge as a move command.
  - A client-only fix **fails** (A6). This is on-camera narration material: "it looks fixed, but a modified client could still do it."

#### B03 — Removing an earlier combatant skips the current turn (REPORTED · Medium · state/lifecycle)
- **How it got there:**
  - The tracker keeps an ordered list and a current-turn index.
  - Removal was first written for the "remove the current, defeated creature" case: when the removed entry was current and last, the index wraps.
  - Removing an entry *before* the current one shifts the list, but the index is never decremented, so the highlight silently lands on the next creature.
- **On-camera repro (≈ 15 s):**
  - Setup: reset demo, "combat" variant. Mira is current.
  - Action: the GM clicks remove on Goblin A, who is above Mira in the order.
  - **Before:** the highlight jumps to Bandit and Mira's turn is gone, in both windows.
  - **After:** the highlight stays on Mira.
- **Complaint (Sam):** "Combat order gets weird sometimes. We killed something and it just jumped right over my turn. Our GM had to click back manually."
- **Detecting tests (protocol, different creatures and orders from the fixture):**
  - F2P-1: remove a combatant above the current one → the current combatant's id is unchanged.
  - F2P-2: remove two entries above the current one in a row → still unchanged, and the round is unchanged.
- **Local sentinels (gate):**
  - Removing the current combatant passes the turn to the next creature.
  - Removing a combatant below the current one changes nothing.
  - Next wraps the order and increments the round.
  - Removing the last remaining entry leaves a valid empty tracker.
- **Alternative fixes:**
  - Adjust the index on removal.
  - Store the current combatant's id instead of an index.
  - Recompute the index from that id after every change.

#### B04 — Token drop lands off-cursor when zoomed (REPORTED · Medium · UI/visual, coordinate transform)
- **How it got there:**
  - Zoom-toward-cursor was added, which moved pan into screen space.
  - The drag preview and the ruler were updated to the shared screen→map conversion.
  - The drop handler, in a different file, still does its own older arithmetic: it divides by zoom before subtracting pan. That is correct only at 100% zoom or zero pan.
  - The on-screen "+" zooms around the viewport centre, so it always creates non-zero pan.
- **On-camera repro (≈ 20 s):**
  - Action: in Sam's window, press "+" twice, then drag Mira three squares to the right onto an obvious floor tile.
  - **Before:** while dragging, the preview follows the cursor. On release, Mira jumps several squares away.
  - Control: at 100% zoom (press "fit"), the drop works. This is why the bug went unnoticed.
  - **After:** Mira lands under the cursor at every zoom.
- **Complaint (Sam):** "Dragging my token is really janky on my laptop — half the time it lands a few squares away from where I let go of it."
  - The complaint deliberately doesn't mention zoom. Finding the condition is part of the task.
- **Detecting tests:** browser test.
  - F2P-1: at 200% via the "+" control, drag a token to a target cell's screen centre → its authoritative cell (read from the GM window's token attribute) equals the target.
  - F2P-2: the same at 50% zoom after a background pan.
- **Local sentinels (gate):**
  - A drop at 100% zoom is correct.
  - A ruler at 200% zoom shows the correct distance.
  - A click selects the right token at 200%.
- **Alternative fixes:**
  - Use the shared conversion in the drop handler.
  - Compute the drop from the preview's last map position.
  - Invert the zoom transform matrix.

#### B05 — HP quick-edit heals above maximum (REPORTED · Easy · domain rule, dual path)
- **How it got there:**
  - The token HP quick-edit (APP-86) was added "to make GM tweaks faster".
  - Its server handler does the arithmetic inline for positive numbers (current + amount) instead of calling the shared healing rule, which caps at max.
  - Negative numbers do go through the shared damage rule, so damage still looks right.

- **Local sentinels (gate):**

#### B06 — Whispers leak to other players after a refresh (UNREPORTED · Hard · info leak, lifecycle)
- **How it got there:**

#### B07 — Typed-in initiative sorts as text (UNREPORTED · Medium · data type across the wire, multi-file)

#### B08 — Ghost tokens after the GM switches scenes (UNREPORTED · Medium · client state lifecycle)

#### B09 — Healing from 0 HP keeps old death-save failures (UNREPORTED · Medium · domain rule, lifecycle)
- **How it got there:**

## 6. Hidden test strategy
- **TST-01** The hidden suite shall have two parts:
  - **Protocol tests** (about 180): real WebSocket clients as GM, players and spectators against the agent's server started in test mode.
  - **Browser tests** (about 25): a single system Chrome with separate contexts for GM and player, a fixed 1440×900 viewport, reduced motion, and waits on server acknowledgements rather than sleeps.
  
  Tests assert only on documented protocol messages and rendered UI (A5). Test-mode hooks are used only for setup.
- **TST-02** Tests shall be written **blind**, by an agent that sees only this spec, PROTOCOL.md, RULES.md and TESTING.md, never the implementation. They are then reconciled against the clean app. Every disagreement is resolved by the SRD text or the spec, never by "what the code does". *Why: the equivalent of task 21's three-way check; stops tests from mirroring bugs in the reference.*
- **TST-03** Tests shall check observable behaviour only. They never check exact wording, ordering that the spec doesn't define, internal ids, CSS values, or timing beyond generous limits. Where the spec leaves a choice open (e.g. an error message's wording), tests accept any value.
- **TST-04** The suite shall be split into:
  - F2P tests per bug;
  - local sentinel sets per bug;
  - **13 regression (P2P) groups**, one per subsystem: join/identity/reconnect, scenes and maps, tokens and ownership, visibility and fog, chat and whispers, dice notation and determinism, sheet derivations and rolls, damage/healing/death, conditions and advantage, combat tracker, rests and slots, persistence and export, UI golden path.
  - Additionally, the **original visible suite** is run as its own 14th regression group; agent edits to it are ignored.
- **TST-05** Regression groups shall include the trap rules:
  - a natural 1 always misses;
  - a natural 20 crit doubles dice only;
  - resistance rounds down;
  - temp HP don't stack;
  - advantage and disadvantage cancel;
  - the exhaustion penalty is −2 per level;
  - the concentration DC floor is 10 and cap is 30;
  - the massive-damage death rule;
  - PB at levels 4, 5, 16, 17;
  - the half-caster level-1 slots follow the 2024 table.
- **TST-06** Validation (done once, before freeze; results recorded in the task's metadata):
  1. The clean app passes everything 3 out of 3 times.
  2. Each bug alone fails exactly its own F2P tests. Everything else passes.
  3. All 11 together fail every F2P test and nothing else.
  4. Every alternative fix (CAT-04) passes.
  5. The visible suite is green on both the clean and all-bugs builds.
  6. Two "delete the feature" controls are each caught by their local sentinels: disabling nudge entirely, and dropping all drag streaming.
- **TST-07** The grader shall rebuild from a pristine scaffold:
  - It uses the frozen lockfile and pre-installed dependencies, and allow-list copies **only the agent's source directories** (the three packages' source and the data dir).
  - It ignores the agent's changes to package manifests, lockfile, configs, tests and node_modules.
  - It builds the client, starts the server on a free loopback port in test mode, and runs the suite.
  - If the build or server start fails, the result is recorded as "did not build".
- **TST-08** Browser tests may retry once, and only for a browser or infrastructure error (not an assertion failure). A test counts as failed only if it fails on both attempts. Protocol tests never retry.
- **TST-09** A full grade shall take ≤ 10 min on Josh's machine: about 45 s build, about 1 min protocol, about 4 min browser. It uses one Chrome at a time and runs serially (task 18 memory lesson).

## 11. Constraints
- **Offline at runtime.** The workspace, grader and app make no network calls. Tailscale is deployment only. Dependencies are pre-installed from a committed lockfile, and the pristine copy lives in the bench cache.
- **No new dependencies in 22a.** The grader ignores manifest changes, so an added package fails the build. The README states this.
- **Licensing.**
  - SRD 5.2.1 CC-BY-4.0 content only, with the required attribution.
  - "5E-compatible" is the only system reference; no product-identity names.
  - Sample maps and token art are original to the project, with a declared license.
  - No art pulled from any dataset.
- **Security.**
  - GM keys come from a cryptographic source.
  - The upload size limit is enforced, and stored file names are generated by the server (no path traversal).
  - Test mode is off by default and loopback-only.
  - Every outbound message is projected per viewer.
- **Performance.**
  - 8 clients and 50 tokens per scene.
  - Drag stream ≤ 20 Hz.
  - Local move-to-broadcast latency < 100 ms.
  - First load < 3 s on localhost.
  - Grade ≤ 10 min.
- **Determinism.** All randomness in game logic goes through the seeded server dice. Nothing in rules or tests depends on wall-clock time.
- **Negative assertions.** The app shall not include:
  - accounts or passwords;
  - cloud or network features;
  - dynamic lighting;
  - AoE automation;
  - multiclassing;
  - any backlog item (§3);
  - canvas/WebGL rendering libraries;
  - analytics;
  - bug hints in code or docs.
- **Size.** 15–25k non-blank lines including tests (APP-142). Also no source file over 500 lines, per Josh's global rule: the bugs have to live in navigable files, not monoliths.
