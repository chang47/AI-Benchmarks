# Independent review — Task 22, “Broken Tabletop”

## A. My spec plan

**Make a session-capable tabletop, not an incomplete general-purpose rules engine.** Ship `22a` as an 11-bug repair task and `22b` as a separate, initially unscored feature-growth task, both derived from one clean app. The clean app must survive a scripted 45-minute mock encounter with a GM and two players before it becomes a benchmark. The 120-minute limit applies to an agent *repairing or extending* the app, not to building the reference.

**Hard core boundary.** One Node/TypeScript authoritative server serves a Vite/React/TypeScript client and WebSocket protocol on one port. A game has cryptographically random GM/player rejoin capabilities; browser-window-local identity survives refresh. The GM can create and activate scenes, upload a local map, set a square grid, manually reveal/hide fog, place and hide tokens, and control initiative. Players can join with a link, own a character, move only owned tokens, pan/zoom, use a ruler, chat, whisper, roll server-side deterministic dice, and consult a small vendored SRD compendium. Sheets expose six abilities, proficiency/skills, attacks, HP/temp HP/death saves, conditions, slots and freeform notes; rules automate **only explicitly enumerated** derivatives and transactions (checks, attacks, damage/healing, death saves, slots, short/long rests). Server-side viewer projection protects secrets on *every* snapshot, event, chat-history replay and asset request. Autosave and restart recovery are mandatory. The UI must have legible GM/player banners, accessible buttons, and a fixture reset that produces camera-ready two-window examples. Implement 2024 SRD rules only where tested; do not imply full 5E automation.

**Backlog is genuinely excluded from the baseline:** multiclassing and class-feature automation, automated spell/AoE resolution, target-side condition automation, a character-builder wizard, dynamic lighting/walls, handouts, ping, drawing, mobile optimization, macros, undo, music, advanced permissions and external VTT imports. In particular, full level-1-to-20 slot automation for all 12 classes, 40 equipment entries and 35 spells are **not prerequisites** for a real session with three prebuilt characters. Prefer ~12 carefully verified spells, ~12 distinct SRD creatures, two original sample maps, and editable freeform fields to a broad but falsely reassuring compendium. Expand only if reference, tests and review still fit 15–25k nonblank source/test lines.

**Rules/content contract.** Cite the SRD 5.2.1 PDF alongside each adopted rules table; vendor only reviewed CC-BY-4.0 text/data with the *exact required attribution* in About and distribution docs, and license original art separately. Avoid non-SRD setting and product branding in app copy, but explicitly exempt legally required attribution from a prohibited-term scan. Dice use a per-game seeded generator for game outcomes, independent from cryptographically generated keys. Test mode may load a fixture and enqueue die faces on loopback, but must not modify rules or turn permission checks off. Define the documented protocol's state replacement semantics, command acknowledgements, generic authorization errors, visibility filters and persistence before implementation.

**Bug catalog.** These are specific prospective patches, not permission to accept a merely plausible narrative: implement every clean pathway first, then verify each stored patch both alone and in the combined buggy build. Every row includes the camera-visible bad→good outcome and a hidden fail→pass (F2P) check; also require adjacent pass→pass (P2P) sentinels. Reset the fixture before each repro. The scripts below use at most GM + Sam windows and each targets <60 seconds.

For B11, **do not call 1×1 rectangle reveal or whole-map rectangle reveal a P2P sentinel**: an exclusive-end loop breaks both on the all-bugs baseline.

**Grade and packaging.** Freeze observable protocol, fixture, UI hooks, test mode, F2P/P2P item ids and scores before planting. Use roughly 80–120 socket/integration assertions and 10–15 carefully batched Playwright scenarios; benchmark actual Windows wall time, not an estimated number. Browser tests wait for versioned ack/snapshot transitions, never animation sleeps; any assertion failure is final. An independent spec-only test author reviews tests against the clean app. Require clean 3/3 green, each patch alone and all 11 together red on intended F2P but green on **every** P2P, plus representative alternative fixes and disable-feature controls. Grade a fresh isolated build with a frozen dependency cache and frozen project scaffold; copy agent-owned source/data but **never** agent tests, hooks, build scripts or dependencies. Reject broken builds as 0. Suggested fixed points: reported 10/8/8/8/6 (40); unreported 8/5/5/5/3/3 (29) gated on both tests and a 2-of-3 FINDINGS.md behavior match. Penalize −4 per failing independent regression group, floor 0; publish a per-bug itemized result. Three-vote judges only decide whether a finding actually describes the unreported behavior, not whether code works. `22b` gets an unscored first-round report: regression preservation, leakage checks for new messages, and at most three demonstrated additions selected from a frozen backlog checklist; defer any scored novelty/utility bands until calibrated examples exist.

**Top risks and gates.** Before product work, spike offline Windows install/build plus benchmark workspace preparation, text-judge integration and ten-minute grading. Then implement the authorization/projection contract, smallest playable slice, correct rules transactions, test-mode fixture, and browser polish; only then author blind tests, validate patches/controls and freeze. One human must play the clean app, run all 11 before/after replays with a stopwatch, inspect source attribution and review the validation matrix. The main risks are a fake-playable rules buffet, cross-bug interference, exploitably public GM/player links, leaking assets outside WebSockets, Windows browser timing, and the large additional harness implementation. Tailscale is optional transport for friends, not a dependency of localhost/offline play; a public Funnel link needs explicit disclosure and server-side capability/asset checks.

## B. Adversarial critique of draft v0

1. **An actual contradiction invalidates its bug-validation promise.** B11's exclusive-end loop does nothing to a 1×1 reveal and omits the last row/column of a full-map reveal. Yet both are listed as P2P sentinels, while CAT-05/TST-06 require *every* P2P green on the all-bugs build. Move those checks to B11 F2P or change the mechanism before freeze. Likewise B09's requirement that *becoming Stable* reset death-save tallies is absent from APP-83: the SRD explicitly says both tallies reset on regaining HP **or becoming Stable** (SRD 5.2.1 PDF, pp. 17–18). B09's sentinel must test the independently correct stabilize path.

2. **The license scanner would flag the legally mandatory attribution.** APP-121 says the entire repository contains none of the product-identity terms, including “Wizards of the Coast”; APP-120 requires the verbatim attribution naming Wizards of the Coast LLC, and the draft itself contains named product terms in docs. Scope the scan to player-facing branding and curated game data, exempt exact required attribution and benchmark design docs, and audit derived dataset notices separately. A hand-checked SRD subset does not inherit unrestricted rights to dataset-hosted illustrations.

3. **APP-12 and B01 conflate identity, fog and ownership.** “Player-owned tokens … always visible to all players” can expose a teammate's location in concealed cells; B01's own sentinel only requires the owner to see an owned token. Decide whether ownership grants visibility to owner alone or whole party and apply it to snapshots, drags, tracker and reconnect. A per-viewer *socket* check must inspect all messages and metadata, not just the rendered hidden token. Moreover APP-20's map/media endpoints can bypass WebSocket filtering: asset access must be authorized per viewer/active scene; export and GM notes must be GM-only.

4. **Calling 15–25k lines a “tight” scope is not credible with the proposed rules breadth.** Twelve classes through level 20, 35 spells, cast-slot spending, 25 monsters with independent multiattacks, condition automation, 40 equipment entries, import/export including binary maps, mouse-coordinate UI, 205 hidden tests and real polish exceed the budget unless major surfaces are paper-thin. Spell “casting” promises prepared-slot/concentration automation but not how targets, spell saves, healing or effects work; users will expect it to function. Explicitly make freeform tracking a first-class feature and move unsupported automation to backlog. Split a vertical-slice budget by *implemented behavior*, not approximate LOC allocations.

5. **Several rules are left unverified unnecessarily, while another is actually specified incorrectly.** The SRD PDF says diagonal movement costs one square (p. 13), damage adjustments precede Resistance then Vulnerability with rounding down (p. 17), and temporary HP expire on finishing a Long Rest (p. 18). The creature index contains Goblin Warrior/Minion/Boss, Bandit and Wolf; choose exact entries. The Short Rest text states for each spent Hit Point Die, roll and add CON, then regain the total (minimum 1); test the actual per-die operation, not a guessed post-hoc floor on an aggregate. More importantly APP-83 omits reset on stabilization. Verify conditions, concentration and spells directly against source text rather than freezing convenient house interpretations as SRD claims. Put edition-specific simplifications in RULES.md, not in unchecked bracketed acceptance criteria.

6. **B07's “validator loosened for a notes field” reads like an invented mutation.** A real cause is HTML input's string value surviving serialization and numeric/string mixed comparison; demonstrate the actual comparator and recorded code history. Its mixed typed/rolled F2P can encounter a non-transitive comparator, making ordering engine-dependent; establish a deterministic concrete input and insist on testing the real built app repeatedly. B04 likewise says the bad formula is correct at zero pan, which can be true only for its precise coordinate convention; derive the transform with a known viewport/grid offset and prove both F2P viewports red before writing the complaint.

7. **The blind-test ideal is weakened by underspecified contracts and narrow alternative fixes.** `docs/PROTOCOL.md` must freeze full command schemas, ack ordering, snapshot replacement, room/event semantics, auth errors and visibility through assets. APP-31 says top-left footprint cell under pointer without defining where the user grabs a Large token; browser drag tests can reject legitimate anchor-offset handling. B11 says browser grading permits a client-side fix, but the documented protocol calls its corners inclusive: a UI-only change can make the demonstration pass while raw server clients still receive wrong semantics. Grade the inclusive command contract at protocol level **as well as** UI, or explicitly permit and document different wire semantics; do not claim both.

8. **The requested run isolation and copied workspace are new software, not a footnote.** Existing `bench.json` supports `artifactDirs` but not an exclusion rule for a cloned monorepo with `.git`, node_modules and dist; existing graders copy output as `src/`. Without bounded collection, committed `runs/<id>/output/` ceases to be “small,” and grading multiple harnesses exhausts disk. Prove pristine scaffold + frozen lockfile/cache on Windows, explicit source allowlist, excluded generated files, reproducible installed dependency tree, and offline network denial *before* finalizing packaging. Hashing a scaffold is useful only if the grader verifies that same scaffold and never loads agent-modified scripts through a source directory.

9. **Ten-minute grade and 2.5-hour human review are projections, not acceptance evidence.** Twenty-five browser cases, ~180 protocol cases, client rebuild, backend start, three judge votes for up to six findings and Chrome setup may overrun; the validation matrix includes 3 clean runs, 11 single-patch runs, combined run, and 22–33 alternative-fix runs. Automate that pre-freeze batch and record actual per-phase times and resource peaks; human time is spent inspecting exceptions. Use one browser process with isolated contexts/fixtures and no retries for assertion failures.

10. **Gameplay security is broader than the two planted permission bugs.** GM keys in URL fragments avoid HTTP Referer exposure but are still bearer secrets available to client script, screenshots, pasted links and any malicious injected HTML/chat. At a minimum: escape text, reject cross-origin WS upgrades and HTTP mutations where applicable, rate-limit guest joins/uploads/commands, cap chat and image resources, authorize file reads, rotate/revoke invitations, and confirm test-mode endpoints cannot be reached via Tailscale. Otherwise a group using Funnel with no accounts can be disrupted trivially even if every planted bug is fixed. Include security regression sentinels without bloating automated rules.

11. **The 22b rubric is too easy to game.** IDEAS.md counting eight ideas rewards padding; a screenshot of a static panel can satisfy “does it do what FEATURES.md claims?” without proving a state change; “would a group use this?” is an unconstrained taste question. For its unscored round, require a live one-minute script with a measurable before/after, role permission check, restart check if persistent, and regression/leak sniffing. Map feature IDs before grading and prevent splitting one feature into three credits. Freeze scoring only after reviewing concrete positive and negative controls.

12. **Remove faux open questions.** The requester already resolved prompt framing, public leakage tolerance, stack, run limit, security-first bonus and deployment. Pick an app name later without blocking architecture; ship concise RULES.md because it distinguishes intentional scope from defects; do not add a second rebuttal hint to the specified one-extra-line prompt; keep server-security bugs at zero for client-only fixes. The remaining actual decisions are verifiable engineering gates (SRD text, Chrome reproducibility, dependency packaging, score calibration), not reasons to defer the specification.

**Residual risk:** Even after these corrections, an 11-bug matrix embedded in a genuinely session-usable app may exceed one person's validation capacity. Cut automated rules/content before cutting bug independence, socket-level authorization or the two-window demo quality.
