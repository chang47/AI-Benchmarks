# Task 22 — "Broken Tabletop" (slugs 22a fix-it / 22b grow-it) — spec v2 (fused, after debate round 2)

## 0. Feature name and purpose
**Working codename: "Tabletop-22"** (product name TBD, OQ-1; "Lantern" is dropped because a panelist reports it collides with an existing open-source web VTT). This is a self-hosted, offline, 5E-compatible web virtual tabletop that a real group can use for an evening session. The GM runs one Node server and shares a link over Tailscale.

The app is built correct first and proven correct by a hidden suite written blind from the docs. Then **11 realistic bugs** are planted: 5 reported as vague player complaints and 6 unreported.
- **22a** is the bugged build. It tests diagnosing and fixing bugs in a ~20k-line codebase the agent didn't write.
- **22b** is the clean build. It tests product sense: brainstorm what the app needs next, then build it.

Every planted bug is:
- a mistake a real developer would make;
- reproducible by hand in two browser windows in under a minute;
- caught by a deterministic hidden fail→pass test through a documented surface.

---

## 1. Decisions and assumptions (settled unless listed in §13)
- **A1 Scope = one real evening session, not a rules engine.** The app has to survive a scripted 45-minute mock encounter with a GM and two players before it becomes a benchmark. It automates only the rules §2 lists. Everything else is freeform text on the sheet. The app never claims full 5E automation.
- **A2 Rendering uses DOM/SVG elements, not a canvas library.** Tokens, fog and rulers are real elements with accessible roles, names and labels. That makes grading deterministic and probe-able without pixel reads, and keeps dependencies light.
- **A3 Identity lives in each window's URL fragment.** A participant key is never put in a URL query, URL path, cookie or HTTP header. The client sends it only in the first WebSocket message.
  - HTTP requests (asset reads, map uploads, game export) never carry the participant key. They carry a short-lived, single-purpose **ticket** that the server issues over the already-authenticated socket (APP-13).
  - Why this matters: two windows in one browser can be different participants, a refresh keeps identity, the fragment never reaches server logs or Referer headers, and the design survives proxies that rewrite or strip upgrade query strings. A panelist reports Tailscale Serve/Funnel does exactly that; G2 verifies it.
  - Why tickets and not a session cookie: a cookie is shared by every window of a browser on the same origin, so it would break "two windows, two participants".
- **A4 All dice are rolled on the server.**
  - Each game has its own seeded generator. The seed is independent of how keys are generated, which is cryptographic.
  - A documented **test mode** (off by default) can reset state, load fixtures, set the seed and queue forced die faces.
  - No on-camera repro needs forced dice.
- **A5 Grading surface.** Hidden tests use only three things:
  1. the documented wire protocol;
  2. the documented test-mode setup hooks, plus the documented non-test-mode setup path: import, invite join, display name, character claim (used by the parity group and by every F2P's non-test-mode run, CAT-02);
  3. the rendered UI, located primarily by roles and labels and secondarily by a small, pinned set of documented test ids.

  Tests never import internal modules.
- **A6 Where each bug is graded.**
  - A behaviour that is fully observable on the wire, or that a documented protocol contract governs, is graded **at the protocol level**. The server must be correct, so a client-only patch scores 0. This covers security, visibility, and documented contracts such as inclusive fog rectangles.
  - A behaviour whose correct fix could legitimately live on either side is graded **through the browser**. This is only allowed where the documented wire contract doesn't pin the fix to the server. B07 qualifies because initiative is a number on the wire (APP-91).
  - Exactly 3 bugs are browser-graded: B04, B07 and B08.
- **A7 Rules edition.** SRD 5.2.1 (2024 rules), CC-BY-4.0 content only.
  - Rule values the panel cited to the PDF are now written as decided values (§2.13).
  - Hidden-test authoring doesn't start until one named person confirms them against the PDF (gate G0, about 1 h).
  - `RULES.md` ships and states every simplification.
- **A8 What stays secret, and what doesn't.**
  - Unreported bugs are not named anywhere in the shipped 22a workspace, prompt or visible tests.
  - The spec, clean source and patches do live in the public repo (clarification 9).
  - Mitigations:
    - deny web tools where the harness can (§11);
    - scan each run's raw transcript for outbound fetches and for references to the benchmark repo, and flag hits in the report (GRD-03);
    - report per run whether web tools were available.
  - **Residual risk, stated plainly:** denying web tools is not network isolation. Shell HTTP clients and other tools keep network access, and blanket egress denial isn't possible because the agent process needs the network to reach its own model. Round 1 treats web access as an **uncontrolled contamination risk** that is detected and disclosed, not prevented (OQ-3).
- **A9 The protocol and test hooks are a stable public contract.** `PROTOCOL.md` and `TESTING.md` say so, and so does the README ("used by external tools; renaming is a breaking change").
  - Why this matters: a well-meaning cleanup that renames message types would otherwise silently zero the protocol tests.
- **A10 Visibility model** (one rule, applied to every outbound path):
  - A player may receive a token only when **one** of these holds:
    - it is player-owned (party tokens are visible to every player, fog or not);
    - it is not hidden and at least one of its cells is revealed.
  - The GM receives everything.
  - Only non-player-owned tokens can be hidden.

## 2. The correct app — acceptance criteria (EARS)

### 2.1 Games, identity, connectivity
- **APP-01** When the GM creates a game, the system shall issue a secret GM key (≥128-bit, from a cryptographic source) and a separate player invite link. *Why: anyone who reaches a Funnel URL could otherwise take over the table, and seeding dice for tests must never make keys predictable.*
- **APP-02** When a person opens the invite link and enters a display name, the system shall admit them as a player and give them a personal rejoin link. They may claim one unclaimed character or stay a spectator. *Why: friends need nothing but a link.*
- **APP-03** While a window has joined a game, the system shall keep that window's identity in its own URL fragment. It shall authenticate the WebSocket through the first message, never through the URL query (A3).
- **APP-04** When the connection drops, the client shall do three things:
  - show a visible "Reconnecting…" state;
  - reconnect automatically with backoff;
  - resynchronize the full viewer-appropriate state, **replacing** its local state rather than merging into it.

  *Why: real proxied sessions drop sockets repeatedly (panel-reported for Tailscale Serve), so this path runs constantly in real play. It is also a deliberate bug site (B06).*
- **APP-05** The system shall show a presence list with each participant's name, role and online status.
- **APP-06** The server shall serve the built client, the HTTP API and the WebSocket on **one configurable port**, same-origin, with relative URLs and automatic ws/wss selection. *Why: one `tailscale serve`/`funnel` mapping is enough, and Tailscale terminates TLS.*
- **APP-07** If a WebSocket upgrade or a state-changing HTTP request carries an Origin that doesn't match the request's host, then the server shall reject it. *Why: blocks cross-site pages from driving a GM's session.*
- **APP-08** The GM shall be able to take two actions against unwanted access:
  - **regenerate the invite link:** the old link stops admitting anyone, and existing players keep their rejoin links;
  - **remove a participant:** their rejoin link is revoked, their socket is closed, and their character becomes unclaimed.

  *Why: a Funnel link is public-by-URL, and the GM needs a way to recover from a leaked link.*
- **APP-09** The README shall document hosting for a real group:
  - run the server;
  - share it with `tailscale serve` (tailnet friends) or `tailscale funnel` (anyone with the link);
  - what Funnel exposes;
  - never to expose a test-mode server.

  At runtime, the app shall make no network calls beyond its own origin.

### 2.2 Authority, permissions, visibility (the security spine)
- **APP-10** The server shall be authoritative. Every state change is a command the server validates (shape, role, ownership) before applying and broadcasting it. An invalid command gets an error only its sender sees. *Why: players may run modified clients, and the README says so.*
- **APP-11** When a player sends a command targeting a token or character they don't own, the server shall reject it. This covers move, nudge, HP change, sheet edit, condition change and death-save marks. The GM may act on everything. For a hidden or nonexistent target, the rejection shall be identical and reveal nothing.
- **APP-12** The server shall build every outbound message **per viewer**, applying the A10 visibility model.
  - The rule covers every message type and payload field: snapshot, update, drag stream, chat live, chat history, roll cards, tracker, errors and metadata.
  - A player never receives:
    - a token they aren't allowed to see, including its id, name or image;
    - GM-only rolls;
    - whispers addressed to others;
    - monster AC and HP numbers;
    - GM notes.

  *Why: this is what makes a VTT trustworthy, and it is the main site for information-leak bugs.*
- **APP-13** When an HTTP request asks for an uploaded asset (map image, token image), the server shall serve it only against an **asset ticket** it issued to that participant over the authenticated socket. It shall check at request time, not issue time, that the participant is still admitted and is still allowed to see the asset under A10.
  - Players can obtain tickets only for the active scene's map and the images of tokens currently visible to them. The GM can obtain tickets for everything.
  - A ticket names one asset and one participant and grants nothing else. It expires within minutes, and the client can always obtain a fresh one. It travels in the URL path, never the query.
  - Removing a participant (APP-08) invalidates their tickets at once.
  - Asset responses are marked as not storable by shared caches.
  - Map uploads (APP-20) and game export (APP-111) use single-use tickets that only the GM can obtain.
  - Stored file names are generated by the server and unguessable.

  *Why: an image request can't carry the first-message credential, a cookie would merge the identities of windows in one browser (A3), and an Origin check alone is not authentication. Without tickets, assets outside the WebSocket would bypass projection.*
- **APP-14** While a monster token is visible to a player, the player shall see its name and a coarse health state, never exact HP. The states are Healthy, Bloodied (≤ half HP) and Down.

### 2.3 Scenes, maps, grid
- **APP-20** When the GM uploads a map image to a scene (PNG/JPEG/WebP, ≤ 20 MB, type checked), the server shall store it locally under the data directory. *Why: the app works offline with the group's own maps.*
- **APP-21** The GM shall be able to set grid cell size and offset and toggle the grid overlay. The map's size in cells follows from the image.
- **APP-22** The GM shall be able to create, rename and delete scenes, and preview any scene without moving players.
- **APP-23** When the GM activates a scene, the system shall move every player's view to it and show **only** that scene's map, fog and tokens, with no refresh. *Why: this is the "pull players to the forest" moment. It is a deliberate bug site (B08).*
- **APP-24** Every participant shall be able to pan (background drag) and zoom between 25% and 400%. Zoom works by wheel toward the cursor and by the on-screen +, − and "fit" controls, where + and − zoom around the viewport centre. Pan and zoom are per window and never broadcast.
- **APP-25** The app shall ship two original sample maps made for the project (Tavern, Forest Road), with a declared license.

### 2.4 Tokens and movement
- **APP-30** The GM shall be able to place tokens for characters, SRD monsters or plain markers. Each token has:
  - a name label;
  - an image or a coloured initial disc;
  - a size footprint (Tiny/Small/Medium 1 cell, Large 2×2, Huge 3×3, Gargantuan 4×4);
  - an optional owner.
- **APP-31** When a permitted participant drags a token and releases it, the system shall snap it so that the pointer's offset from the token's top-left at grab time is preserved, landing on the grid cell under the pointer. This must hold at **any zoom and pan**. During the drag, a live distance readout in feet is shown. *Why: this is the most-used interaction, and the coordinate transforms are a deliberate bug site (B04).*
- **APP-32** While a token is being dragged, the system shall stream its live position (≤ 20 updates per second) **only to viewers who may currently see that token** under A10. The drag stream obeys exactly the same visibility rule as every other message. *Deliberate bug site (B01).*
- **APP-33** When a permitted participant presses an arrow key with a token selected, the system shall move it one cell, clamped to the map. Any participant may select any visible token to inspect it, but only permitted participants may move it. *Deliberate bug site (B02).*
- **APP-34** The GM shall be able to toggle a non-player-owned token hidden. The GM sees hidden tokens at reduced opacity with a hidden marker; players never receive them.
- **APP-35** Each token shall show an HP bar and condition badges. The GM and the owner see full numbers; everyone else sees the coarse state (APP-14).

### 2.5 Fog of war (manual, cell-based)
- **APP-40** While fog is enabled for a scene, players shall see fogged cells as opaque and the GM shall see them as translucent. Fog is off by default, and enabling it covers every cell.
- **APP-41** When the GM drags a Reveal or Hide rectangle, the system shall change **every cell the rectangle covers, including the cells under both corners**, exactly as the GM's preview showed. `PROTOCOL.md` defines rectangles as inclusive corner cells, and the server honours that for any client. *Deliberate bug site (B11).*
- **APP-42** When cells are revealed or hidden, the tokens that become visible or invisible to each player shall appear or disappear without a refresh.
- **APP-43** The fog layer shall stay responsive (≤ 100 ms to apply a change locally) at 60×60 cells.

### 2.6 Measurement
- **APP-45** Every participant shall have a ruler that measures cell-to-cell distance in feet: each square is 5 ft, and a diagonal step costs one square (5 ft). The ruler is local to the window and correct at every zoom and pan.

### 2.7 Dice and chat
- **APP-50** When a participant sends `/r <expression>` or `/roll`, the server shall roll it and post a roll card showing the expression, every die face, which dice were kept or dropped, and the total. Supported notation:
  - `NdM`, and `dM` with an implied count of 1;
  - `d%` (1–100);
  - `kh`, `kl`, `dh`, `dl`;
  - several groups and constants joined by + and −.

  Limits: 1–100 dice per group and 2–1000 sides. *Why: this is the core social loop, and the implied count is a deliberate bug site (B10).*
- **APP-51** If an expression is invalid or out of limits, then the system shall show a readable error to the sender only and post nothing.
- **APP-52** When a participant sends `/gmr <expression>`, only the GM and the roller shall see the result.
- **APP-53** When a participant sends `/w <name> <text>`, the message shall reach only the named participant(s) and the GM, **both live and in every history replay** (join, reconnect, refresh), whether or not the recipient is online. *Deliberate bug site (B06).*
- **APP-54** The system shall persist the last 500 chat entries per game and replay them on join and reconnect, filtered per viewer (APP-12).
- **APP-55** Roll cards shall highlight a natural 20 and a natural 1 on a d20, and name each source of advantage or disadvantage (for example, "Disadvantage: Poisoned"). All message text shall be rendered as text, never as markup.

### 2.8 Characters and sheets (single-class, levels 1–20)
- **APP-60** A sheet shall hold the following, editable only by the owner and the GM:
  - name, class and level;
  - six ability scores;
  - save and skill proficiencies, with expertise;
  - AC, max HP, current HP and temp HP;
  - speed, hit dice and conditions;
  - exhaustion level and death saves;
  - attacks, typed in by the user (name, ability, proficient flag, extra bonus, damage dice and type);
  - prepared spells from the compendium;
  - freeform features and inventory text;
  - damage resistances, vulnerabilities and immunities;
  - GM notes, visible to the GM only.

  *Why: freeform fields let a real group play while automation stays small.*
- **APP-61** The sheet shall derive the following and never let them be typed in:
  - ability modifiers;
  - proficiency bonus: 2 + floor((level − 1) / 4);
  - skill and save modifiers (expertise doubles proficiency);
  - passive Perception;
  - initiative modifier;
  - spell save DC and spell attack bonus;
  - spell slots from the three SRD tables (full caster, half caster, Pact Magic), for each class's casting type;
  - cantrip damage dice at levels 5, 11 and 17.
- **APP-62** When the owner or GM clicks a check, save, skill, attack, damage roll, initiative or spell, the system shall roll it on the server with the correct modifier and post a roll card.
  - An attack against a targeted token reports HIT or MISS.
  - Players see only HIT or MISS; the GM also sees the AC.
- **APP-63** When an attack roll's d20 shows 20, the attack shall hit and be a critical hit: damage dice are rolled twice and modifiers are added once. A natural 1 shall miss regardless of the total.
- **APP-64** While the roller has one of the conditions below, the system shall apply its effect to the roller's **own** d20 tests. Advantage and disadvantage cancel to a straight roll however many sources of each apply.

  | Condition | Effect on the roller's own d20 tests |
  |---|---|
  | Poisoned | Disadvantage on attacks and ability checks |
  | Blinded | Disadvantage on attacks |
  | Prone | Disadvantage on attacks |
  | Restrained | Disadvantage on attacks and Dex saves |
  | Frightened | Disadvantage on attacks and ability checks (RULES.md: assumes the source is in sight) |
  | Invisible | Advantage on attacks |
  | Exhaustion | −2 × level on every d20 test |
  | Paralyzed, Stunned, Petrified, Unconscious | Automatically fail Str and Dex saves |

  Effects that apply to the target are backlog.
- **APP-65** When a prepared spell is cast, the system shall post a spell card with the spell's text summary, its attack bonus or save DC, and a damage or healing roll button where the compendium entry has one.
  - A leveled spell spends a slot of the chosen level (at least the spell's level), and the cast is refused when none remain.
  - Casting a concentration spell ends any previous concentration and marks the caster as concentrating.
  - Picking targets and applying effects stay manual.

  *Why: this defines exactly what "cast" means, so testers and users don't expect automation that doesn't exist.*

### 2.9 Monsters and compendium
- **APP-70** The GM shall be able to search a vendored SRD 5.2.1 subset of about **15 creatures** (CR 0–8, several types, including multiattack, resistances and condition immunities) and add them to a scene. Each added monster is an independent instance at its stat block's average HP. The subset includes Goblin Warrior (Fey), Bandit and Wolf under those exact names.
- **APP-71** The GM shall be able to roll a monster's initiative, saves, checks, attacks and damage from its stat block. These rolls are GM-only by default.
- **APP-72** Every participant shall be able to browse about **20 spells** (cantrips to 3rd level, mixing attack, save, concentration and ritual spells) and the 15 conditions as a reference.

### 2.10 Damage, healing, conditions, death
- **APP-80** When typed damage is applied, the system shall apply these steps in order, then show the arithmetic to the GM:
  1. immunity makes it 0;
  2. resistance halves it, rounding down;
  3. vulnerability doubles it;
  4. temporary HP absorb damage first;
  5. HP floors at 0.
- **APP-81** When a PC drops to 0 HP, the system shall make it Unconscious and start death saves. If the damage left over after reaching 0 is at least its HP maximum, the PC dies instead. A monster at 0 HP is shown as Down and stays on the tracker until removed.
- **APP-82** When a PC at 0 HP takes damage, the system shall add one death-save failure, or two if the damage came from a critical hit. If that damage is at least the PC's HP maximum, the PC dies.
- **APP-83** When a death save is rolled, the system shall apply the result:

  | Roll or tally | Result |
  |---|---|
  | 10 or higher | success |
  | below 10 | failure |
  | natural 1 | two failures |
  | natural 20 | regain 1 HP and become conscious |
  | three successes | Stable, and both tallies reset to zero |
  | three failures | Dead |

  The owner or GM may also set the marks directly (table correction).
- **APP-84** When a creature regains HP by any route, the system shall cap HP at the maximum. The routes are the heal dialog, the HP quick-edit, a spell, a rest and a natural 20 death save.
  - If the creature was at 0 HP, the system shall also remove Unconscious and **reset both death-save tallies and Stable**.
  - A Dead PC doesn't regain HP.

  *Two deliberate bug sites: B05 (quick-edit) and B09 (the reset).*
- **APP-85** When a creature that already has temporary HP gains more, it shall keep the higher of the two values; temporary HP never stack.
- **APP-86** The GM and the owner shall have an HP quick-edit on the token that takes a signed number. A negative number is untyped damage and a positive number is healing, both through the same rules as APP-80 and APP-84. Untyped damage ignores resistances.
- **APP-87** When a concentrating creature takes damage, the system shall prompt a Constitution save at DC = max(10, floor(damage / 2)), capped at 30. Concentration ends on a failure, or when the creature gains Incapacitated or a condition that includes it.
- **APP-88** The GM and the owner shall be able to add and remove the 15 SRD conditions and set exhaustion 0–6. Exhaustion 6 is death.

### 2.11 Combat tracker
- **APP-90** When the GM starts combat and adds tokens, every participant shall see a tracker with these properties:
  - it is ordered by initiative, highest first;
  - the current turn is highlighted;
  - a round counter starts at 1;
  - hidden combatants are omitted for players, who see "GM's turn" while a hidden combatant is current.
- **APP-91** Initiative values may come from a server roll, an owner roll, or a number the GM types in (for groups rolling physical dice). The tracker every participant sees shall be ordered numerically, whatever the value's source.
  - `PROTOCOL.md` defines an initiative value on the wire as a **number**. The clean server rejects any other type as an invalid command (APP-10).
  - The planted bug loosens exactly that check. So no hidden test sends a non-number initiative or asserts that one is rejected. A fix that restores rejection is welcome but not required, and this is recorded as a deliberate grading gap.
  - Ties go to the higher initiative modifier, then to name order. This is a house rule, documented as such.
  - The GM may drag to reorder, and the order the GM sets is authoritative until the next initiative change.

  *Why numbers only on the wire: this keeps the server contract consistent with browser grading, so a fix in the client, the validator or the comparator is equally correct. Typed input is a deliberate bug site (B07).*
- **APP-92** When the GM presses Next, the highlight shall move to the next combatant. Wrapping past the end increments the round.
- **APP-93** When a combatant is removed, the system shall keep the turn correct:
  - If another combatant was removed, the current creature stays current.
  - If the current creature was removed, the turn passes to the next creature in order.

  No turn is ever skipped or granted twice, and the round doesn't change. *Deliberate bug site (B03).*
- **APP-94** When the GM ends combat, the system shall clear the tracker. The next combat starts at round 1.

### 2.12 Rests and resources
- **APP-100** During a Short Rest, the owner or GM may spend hit dice **one at a time**. Each spend heals the die roll plus the CON modifier, with a minimum of 1. Warlock Pact slots recover.
  - Why one at a time: this keeps the SRD's per-die minimum unambiguous.
- **APP-101** When a Long Rest is taken, the system shall:
  - restore HP to maximum and all hit dice;
  - restore all spell slots;
  - remove one exhaustion level;
  - end temporary HP, death saves and concentration.

### 2.13 Rules provenance
- **APP-105** Each rules table and trap rule shall cite its SRD 5.2.1 page in `RULES.md`. The panel has already cited these to the PDF:
  - diagonal costs one square (p.13);
  - damage-adjustment order and rounding down (p.17);
  - temporary HP end on a Long Rest (p.18);
  - death-save tallies reset on regaining HP or becoming Stable (pp.17–18);
  - the creature names (Goblin Warrior, Bandit, Wolf; goblins are Fey).

  Gate G0 confirms every citation before any hidden test is written. Any value that differs is corrected in the spec, not in the tests.

### 2.14 Persistence
- **APP-110** The server shall autosave each game within 2 s of a change and restore everything after a restart: scenes, tokens, fog, sheets, tracker (including round and current turn), and chat history.
  - The writes are atomic: temp file, then rename, with a bounded retry on transient Windows file-lock errors.
- **APP-111** The GM shall be able to export a game to one self-contained JSON file, with uploaded images included, and import it as a new game.
  - **The round trip covers all game state:**
    - scenes and maps;
    - tokens, with their hidden flags and character links;
    - fog;
    - sheets;
    - the tracker, including round and current turn;
    - chat history, including each entry's GM-only flag and whisper recipients.
  - **Import carries no participants or credentials.** It returns fresh GM and invite credentials, and every character arrives unclaimed. Every private chat entry becomes visible to the GM only, because its original recipients no longer exist.
  - Import follows the same admission rule as creating a game, with the Origin check (APP-07) and a size cap.

  *Why: backups, and the documented setup path for every non-test-mode run: the parity group and every F2P's twin (CAT-02). Players are recreated through invite join and character claim.*

### 2.15 Content, licensing, branding
- **APP-120** The verbatim SRD 5.2.1 attribution sentence shall appear in the README, in `data/LICENSE-SRD.md` and in an in-app About panel. The app describes itself only as "5E-compatible".
- **APP-121** Player-facing UI strings, app branding and curated game data shall contain none of the product-identity terms in the SRD research note. A visible test scans those surfaces.
  - The exact required attribution text is exempt, and benchmark design documents are out of scope.
  - Vendored data drops upstream image and URL fields, and no art is taken from any dataset.
- **APP-122** Game data shall be a small, normalized, hand-checked subset:
  - about 15 creatures and about 20 spells;
  - the core data of all 12 classes (hit die, save proficiencies, casting ability and type);
  - 15 conditions and 18 skills;
  - the three slot tables.

  There is no equipment compendium; attacks and inventory are entered on the sheet.

  Game data and its license live in the repository-root `data/` directory. They are never placed under a source tree the grader copies (TST-07). *Why: this makes "agent edits to rules data are ignored" a structural fact rather than a filter the grader would need, so editing a stat block or table can't pass as a fix.*

### 2.16 Determinism and test mode
- **APP-130** While the server runs in test mode, it shall expose documented hooks to:
  - reset;
  - load a named fixture with fixed participant keys;
  - set a game's dice seed;
  - queue forced die faces.

  Test mode:
  - is an environment flag, off by default;
  - binds to loopback only;
  - **requires a per-process hook secret** supplied at start-up.

  *Why a secret: `tailscale serve` proxies from loopback, so the loopback bind alone doesn't protect the hooks.*
- **APP-131** Test mode shall change no game rule, permission, visibility or client behaviour. Two things enforce this: the hidden "test-mode parity" group (TST-04) and the non-test-mode run of every F2P (CAT-02).
- **APP-132** With the same seed and the same command sequence, the server shall produce the same dice results.
- **APP-133** A `demo` launcher shall start the server in test mode and load the "Sunken Tavern" fixture. It prints the GM link **masked** (the full link is copied to the clipboard or written to a local file) and each player's link. It can also start a second instance on another port. *Why: the GM key must never appear on camera.*

### 2.17 Codebase shape
- **APP-140** The repository shall be one npm-workspaces monorepo with three packages:
  - `shared`: rules, dice, protocol types, validators;
  - `server`: Node + TypeScript + WebSocket, persistence, projection;
  - `client`: Vite + React + TypeScript.

  One root check command runs typecheck, lint and the visible tests.
- **APP-141** The shipped repo shall include:
  - a README (features, run, host, authoritative-server model, "no new dependencies", "protocol is a stable contract");
  - `docs/PROTOCOL.md` documents:
    - every message and command shape, with initiative as a number;
    - acknowledgement ordering;
    - replace-versus-merge semantics for snapshots;
    - generic authorization errors;
    - the inclusive-rectangle convention;
    - the ticket mechanism for assets, uploads and export;
    - the invite-join, claim and rejoin flow;
    - the visibility contract (A10), including assets;
  - `docs/TESTING.md`: test mode, the fixture, the pinned test-id set, and the non-test-mode setup path (import, then invite join and claim);
  - `docs/RULES.md`: the implemented rules with page citations, and the simplifications.
- **APP-142** The codebase shall measure 15–25k non-blank lines of TS/TSX/CSS, counting all tests but excluding data JSON and the lockfile.

  - The line count is measured with a frozen counter at G1.
  - **Scope is cut only by spec amendment.** If the count trends over the limit, the spec, docs and affected hidden tests are revised in the same recorded change, and no acceptance criterion is ever waived silently. Amendments land before blind authoring (build step 6) wherever possible. After that, the amendment names each hidden test it removes.
  - Pre-approved amendment candidates, in order:

- **APP-143** The visible suite shall be modest and realistic: about 50 unit and integration tests plus at most 2 browser smoke tests.

## 4. How the design creates good bug sites
- **Parallel paths to one invariant:**
  - drag vs nudge (ownership);
  - heal dialog vs quick-edit (the cap);
  - live chat vs history (whisper filtering);
  - update vs drag stream (visibility).
- **Per-viewer projection:** every new outbound path must go through it.
- **An ordered list plus a cursor:** the tracker's index goes stale.
- **Coordinate transforms:** the conversion between screen and map under zoom, pan and grid offset.
- **Client cache vs server truth:** merging where the code should replace.
- **Typed values crossing the wire:** checking that text parses as a number, then storing the text.
- **Boundary conventions between packages:** an inclusive protocol rectangle meets an exclusive loop.
- **Rules state added after the rules that must reset it:** death saves came after healing.
- **Parser rewrites:** an implied default gets lost.

## 5. Planted-bug catalog

### 5.1 Catalog-level acceptance criteria
- **CAT-01** Each bug shall be a stored patch against the clean app that reads like ordinary product code:
  - no comment, TODO, name, log line or test mentions the bug, and any contradicting clean comment is adjusted;
  - the diff is ≤ 40 changed lines, possibly across several files;
  - the patch **lives entirely inside the allow-listed source directories** (TST-07).
- **CAT-02** Each bug shall have ≥ 1 hidden fail→pass (F2P) test that:
  - fails with the bug alone and with all 11 applied;
  - passes on the clean app;
  - is stable 3/3.

  **Every F2P, protocol or browser, also runs against a non-test-mode server.** That server is set up through import, then invite join and character claim (A5). Credit requires both runs to pass.
  - An F2P that needs forced faces gets a non-forced **twin** that asserts structure and range instead of exact totals (B09, B10).
  - *Why: without this, a fix gated on test mode would go unseen for the dice bugs and for all three browser bugs. The parity group alone samples only protocol behaviours that need no dice.*
- **CAT-03** Each bug shall have **local sentinels**: pass→pass checks of neighbouring behaviour that a delete-the-feature "fix" would break.
  - Every sentinel must pass with its own bug applied, with any other single bug applied, and with all 11 applied. Anything a bug breaks is that bug's F2P, never a sentinel (TST-10).
  - Sentinels gate that bug's points.
- **CAT-04** Each bug shall be validated against 2–3 alternative correct fixes. Each one must pass the bug's F2P tests, its sentinels and every regression group.
- **CAT-05** No bug shall crash the app on load, fail the build, or break anything beyond its own symptom. With all 11 applied, every regression group stays green.
- **CAT-06** Each bug shall have an on-camera repro with these limits:
  - it starts from "reset demo" and takes ≤ 60 s by hand;
  - it uses at most two windows (GM + Sam);
  - its outcome is visibly wrong to a non-coder;
  - the same script shows the correct outcome on the fixed build;
  - the whole repro set takes ≤ 10 min.

  Each repro's "before" is confirmed on the real built app before its complaint or F2P is frozen.
- **CAT-07** Hidden-test inputs shall differ from the complaints and repros: other creatures, numbers and cells.
- **CAT-08** The bugged repo shall be generated **once**, on the build machine, by applying all patches, and then frozen as an artifact with its hash in the manifest. Packaging never re-applies patches. *Why: task 18's line-ending lesson.*

### 5.4 Bug entries

#### B01 — Live drag stream leaks tokens the player may not see (REPORTED · Hard)
- **How it got there:**
  - Live movement came after the projector. For smoothness, the drag handler relays "token is being dragged" events to everyone else in the room, skipping projection because the event "only carries a position".
  - The event also carries display basics (name, image reference, size) so that clients with stale state can draw the moving token.
  - The client's drag layer draws any token id it receives.
  - On release, the final update goes through the projector, so the token vanishes again.
- **Repro (≈ 30 s):** the GM and Sam's windows sit side by side, and Sam sees a dark cellar. The GM slowly drags a hidden Goblin Warrior across the cellar.
  - **Before:** a labelled goblin glides across Sam's map, then disappears on release.
  - **After:** nothing appears for Sam. Once the GM un-hides the goblin, it appears at its final cell.
- **Complaint (Sam):** "Kind of spoiled last session — I could see monsters before our GM revealed them. Not the whole time, they just kind of showed up for a bit while things were moving?"
  - The wording covers both the hidden flag and fog, matching the single A10 invariant.
- **F2P (protocol, sniffing player socket):**
  1. The GM streams a drag of a hidden token → no message to the player contains the token's id, name, image reference or an asset ticket for its image.
  2. The GM drags a non-hidden monster that stays entirely inside fogged cells → no message about it reaches the player.
- **Sentinels:**
  - A visible token's drag is streamed to players.
  - A hidden token's drag is streamed to the GM.
  - A non-hidden token dragged from fog into revealed cells becomes visible to players.
  - A player-owned token under fog is streamed to all players.
  - Un-hiding delivers the token at its current cell.
- **Alternative fixes:**
  - Route the drag event through the projector.
  - Filter recipients by the visibility predicate.
  - Compute the stream per recipient.

  A client-only "ignore unknown ids" fix **scores 0 by design**.

#### B02 — Keyboard nudge skips the ownership check (REPORTED · Medium)
- **How it got there:**
  - Nudge was added later as its own command.
  - Its server handler checks that the token exists and clamps the move, but never calls the ownership guard that the move handler uses.
  - The client's keyboard handler acts on whatever token is selected, and any player may select a visible token.
- **Repro (≈ 20 s):** Sam clicks Brother Aldric and presses → three times.
  - **Before:** Aldric walks three squares in both windows.
  - **After:** Aldric doesn't move in either window, apart from a momentary snap-back in Sam's. How the refusal is displayed is left open.
- **Complaint (Jo):** "Pretty sure someone else in our group can move my character. I left my cleric by the bar and next thing I know he's across the room. Nobody's owning up to it 😅"
- **F2P (protocol):**
  1. A raw player socket nudges a token that player doesn't own → rejected, and the GM sees the token's cell unchanged.
  2. The same attempt on a hidden monster → rejected, with an error identical to the one for a nonexistent id.
- **Sentinels:**
  - The owner can nudge their own token.
  - The GM can nudge any token, including hidden ones.
  - The owner's drag-move still works.
  - Nudging clamps at the map edge.
- **Alternative fixes:**
  - A guard in the nudge handler.
  - A central permission check for all token commands.
  - Implementing nudge as a move.

  A client-only fix **scores 0**. On camera: "it looks fixed, but a modified client can still do it."

#### B03 — Removing an earlier combatant skips the current turn (REPORTED · Medium)
- **How it got there:**
  - The tracker stores a list and a current index.
  - Removal was written for the "remove the current, defeated creature" case, where the index wraps.
  - Removing an entry *before* the current one shifts the list without decrementing the index.
- **Repro (≈ 15 s):** in the "combat" variant, with Mira current, the GM removes Goblin Warrior A.
  - **Before:** the highlight jumps to the Bandit.
  - **After:** the highlight stays on Mira.
- **Complaint (Sam):** "Combat order gets weird sometimes. We killed something and it just jumped right over my turn. Our GM had to click back manually."
- **F2P (protocol, different combatants and orders):**
  1. Remove a combatant above the current one → the current id is unchanged.
  2. Remove two entries above it in a row → the current id and the round are unchanged.
- **Sentinels:**
  - Removing the current combatant passes the turn to the next creature.
  - Removing a combatant below the current one changes nothing.
  - Next wraps and increments the round.
  - Removing the last entry leaves a valid empty tracker.
- **Alternative fixes:**
  - Adjust the index on removal.
  - Store the current id instead of an index.
  - Recompute the index from the id after every change.

#### B04 — Token drop lands off-cursor when zoomed (REPORTED · Medium)
- **How it got there:**
  - Zoom-toward-cursor moved pan into screen space. The preview and the ruler were switched to the shared screen→map conversion.
  - The drop handler, in another file, keeps its older arithmetic: it divides by zoom before subtracting pan.
  - That is only right at 100% zoom or zero pan, and the "+" control always creates non-zero pan.
  - Before freeze, the exact wrong formula is derived for the real viewport and grid offset, and both F2P viewports are proven to fail.
- **Repro (≈ 20 s):** Sam presses "+" twice and drags Mira three squares right onto a marked floor tile.
  - **Before:** the preview follows the cursor, but on release Mira lands several squares away.
  - **Control:** after "fit" (100%), the drop is correct.
  - **After:** Mira lands on the target at every zoom.
- **Complaint (Sam):** "Dragging my token is really janky on my laptop — half the time it lands a few squares away from where I let go of it." The complaint deliberately leaves out zoom.
- **F2P (browser, Medium token):**
  1. At 200% zoom (via "+"), drag to a target cell's centre → the token's authoritative cell, read from the GM window, equals the target.
  2. The same at 50% after a background pan.
- **Sentinels:**
  - A drop at 100% is correct.
  - The ruler at 200% shows the right distance.
  - A click at 200% selects the right token.
- **Alternative fixes:**
  - Use the shared conversion in the drop handler.
  - Take the drop from the preview's last map position.
  - Invert the transform.

#### B05 — HP quick-edit heals above maximum (REPORTED · Easy)
- **How it got there:** the quick-edit's server handler adds positive numbers inline instead of calling the shared (capped) healing rule. Negative numbers do go through the shared damage rule.
- **Repro (≈ 10 s):** the GM enters +10 on Aldric (20/24).
  - **Before:** 30/24, with the bar overflowing.
  - **After:** 24/24.
- **Complaint (Jo):** "Our cleric patched me up after the fight and my HP ended up higher than it's supposed to be. Free HP is nice but I don't think that's how it works."
- **F2P (protocol):**
  1. 11/37 with +40 → 37/37.
  2. 36/37 with +5 → 37/37.

  The tests reach 11/37 and 36/37 through documented typed-damage commands, in both modes. No set-HP hook is added.
- **Sentinels:**
  - 11/37 with +3 → 14.
  - −8 with 5 temp HP → temp 0 and HP down by 3.
  - The heal dialog caps at max.
  - Dialog healing from 0 restores consciousness.
- **Alternative fixes:**
  - Call the shared healing rule.
  - Cap inline.
  - Route the quick-edit through the heal command.

#### B06 — Whispers leak to other players in history replay (UNREPORTED · Hard)
- **How it got there:**
  - History replay was written when the only private entries were GM-only rolls, so its filter checks only that flag.
  - Whispers came later. The live path filters by recipients, but the history filter was never updated.
- **Repro (≈ 25 s):** the GM sends "/w Jo The innkeeper is lying." Sam sees nothing, then presses F5.
  - **Before:** the whisper appears in Sam's chat.
  - **After:** it never appears for Sam.
- **F2P (protocol):**
  1. A whisper from player A to B, then player C reconnects → neither the whisper's text nor its id is in C's history.
  2. A GM whisper to B, then a new player D joins → it is absent from D's history.
- **Sentinels:**
  - The recipient's history includes the whisper.
  - The GM's history includes every whisper.
  - GM-only rolls stay hidden.
  - Public messages replay in order.
- **Alternative fixes:**
  - One shared visibility predicate for both paths.
  - Add a recipient check to the history filter.
  - Keep a separate history per viewer.
- **Why an agent can find it:** an agent that fixes B01 by auditing every outbound path should also find this one.

#### B07 — Typed-in initiative sorts as text (UNREPORTED · Medium)
- **How it got there:**
  - Manual entry sends the input field's raw text, a string that falls outside the documented number-only contract (APP-91).
  - The server validator was loosened to accept anything that *parses* as a finite number, and it stores the **original** value ("validate the cast, store the original").
  - The comparator chain (initiative, then modifier, then name) compares with greater-than.
  - Rolled values are numbers and order correctly; two typed values compare as text.
- **Repro (≈ 20 s):** the GM starts a new combat with Mira, Aldric and the Bandit and types 9, 14 and 21.
  - **Before:** the tracker reads 9, 21, 14 in both windows.
  - **After:** 21, 14, 9.
  - The repro types values for every combatant, because mixing typed and rolled values makes the comparison non-transitive.
- **F2P (browser; every value typed, so the "before" order is deterministic):**
  1. Type 7, 12 and 30 → displayed 30, 12, 7 (the buggy order is 7, 30, 12).
  2. Type 5, 40 and 100 → displayed 100, 40, 5 (buggy: 5, 40, 100).
- **Sentinels (all pass with the bug):**
  - Rolled initiatives order correctly.
  - The documented tie-break holds for rolled values.
  - Drag-reorder persists, including across a reconnect.
  - With typed values, Next always moves the highlight to the row displayed directly below the current one, wrapping from the last row to the first.
- **Alternative fixes:**
  - Parse in the client, which restores the wire contract.
  - Coerce and store the number in the server validator.
  - Compare numerically in the comparator.

  Why browser grading: all three are legitimate, and the number-only wire contract (APP-91) means none of them leaves a documented server behaviour broken.

  A **display-only client re-sort is not a fix and scores 0.** It leaves the server's order wrong, so it fails the drag-reorder and Next sentinels.

#### B08 — Ghost tokens after the GM switches scenes (UNREPORTED · Medium)
- **How it got there:**
  - Scene activation reuses the client's incremental-resync handler, which **merges** incoming tokens into the cache.
  - The GM's own "open scene" path **replaces** the cache, so the GM never sees the problem.
  - A refresh clears the ghosts.
- **Repro (≈ 20 s):** the GM activates Forest Road.
  - **Before:** Sam sees the Wolves among the Innkeeper, Mira and Aldric standing in the trees. After F5 they're gone.
  - **After:** only the forest tokens show.
- **F2P (browser):**
  1. After activation, the player's rendered token set equals exactly the new scene's visible tokens.
  2. Switching A→B→A shows only scene A's tokens, with no duplicates.
- **Sentinels:**
  - After a reconnect, a player shows the correct tokens without duplicates.
  - The GM's scene preview doesn't move players.
  - The new scene's fog renders correctly.
- **Alternative fixes:**
  - Replace the cache on activation.
  - Clear the cache, then merge.
  - Key the cache by scene.

#### B09 — Healing from 0 HP keeps death-save marks (UNREPORTED · Medium)
- **How it got there:**
  - The healing rule predates death saves.
  - When death saves were added, the damage-at-0, natural-20 and stabilize paths were updated.
  - Healing still only removes Unconscious.
- **Repro (≈ 30 s):** the GM sets Aldric to 0 HP, clicks two failure marks, then heals 5 through the dialog.
  - **Before:** Aldric wakes up with two red marks. One more failure after the next drop kills him.
  - **After:** the marks clear.
- **F2P (protocol, forced dice):**
  1. At 0 HP, fail two saves (forced 4, 7), then heal 3 → tallies 0/0 and not Stable.
  2. A Stable PC healed for 1 → Stable is cleared, and a later drop to 0 starts fresh.
- **Non-test-mode twin:** at 0 HP, the GM sets two failure marks directly (APP-83), then heals 3 → tallies 0/0. F2P 2 has no twin, and twin 1 is enough to catch a fix gated on test mode.
- **Sentinels:**
  - A natural 20 sets HP to 1 and resets the tallies.
  - Three successes make the PC Stable and reset the tallies (the independent stabilize path).
  - A natural 1 counts as two failures.
  - Damage at 0 adds one failure, or two on a crit.
  - Three failures mean Dead.
  - Healing a Dead PC does nothing.
- **Alternative fixes:**
  - Reset inside the healing rule.
  - A single "HP left 0" transition function.

#### B10 — `/r d20` with no count rolls no dice (UNREPORTED · Easy)
- **How it got there:**
  - The keep/drop rewrite made the count optional but lost the "missing count means 1" default.
  - An empty count parses as not-a-number, so zero dice are rolled.
  - Sheet buttons always send explicit counts.
- **Repro (≈ 10 s):** Sam types "/r d20+3".
  - **Before:** no dice, total 3.
  - **After:** one d20 plus 3.
- **F2P (protocol, forced faces; totals are pinned, not just dice counts):**
  1. "d12+1" with a forced 7 → one die, total 8.
  2. "d%" with a forced 42 → one die, total 42.
  3. "2d6+d4" with forced 3, 5, 2 → three dice, total 10.
- **Non-test-mode twin (seeded, unforced):**
  - "d12+1" gives exactly one face in 1–12, and the total is that face + 1.
  - "d%" gives exactly one face in 1–100, and the total equals it.
  - "2d6+d4" gives exactly three faces within their ranges, and the total is their sum.
- **Sentinels:**
  - "1d20", "4d6kh3", "2d8−1" and "10d6" give correct totals with forced faces.
  - An invalid expression errors to the sender only.
- **Alternative fixes:**
  - Default the count at parse time.
  - Normalize the expression first.

#### B11 — Fog rectangles miss the last row and column (UNREPORTED · Easy)
- **How it got there:**
  - PROTOCOL.md defines inclusive corner cells, and the client sends them.
  - The server's loop treats the end as exclusive, a leftover from when the tool sent pixel-derived ends.
  - A 1×1 rectangle therefore changes nothing, and larger rectangles miss their last row and column.
- **Repro (≈ 20 s):** the GM reveals the whole cellar, and the GM preview covers all 5×4 cells.
  - **Before:** Sam sees a dark strip along the right column and bottom row, and no Bandit.
  - **After:** the whole cellar is revealed and the Bandit appears.
- **F2P (protocol, player socket; a client-only "send end+1" fix violates the documented contract and scores 0):**
  1. Reveal a 3×2 block → all six cells are revealed in the player's fog state, and a token in the far corner is delivered.
  2. Hide a 2×2 block → all four cells are fogged, and a far-corner token is withdrawn.
  3. Reveal a single cell → that cell is revealed.
- **Sentinels (all unaffected by the bug):**
  - Cells outside the rectangle are unchanged.
  - Enabling fog covers every cell.
  - A token in an interior revealed cell is delivered without a refresh.
  - The GM receives the same fog state as players.
- **Alternative fixes:**
  - An inclusive server loop.
  - Normalize the rectangle once at the protocol boundary.

## 6. Hidden test strategy
- **TST-01** The hidden suite has two parts:
  - **Protocol tests** (about 120–180): real WebSocket clients as GM, players and spectators.
  - **Browser tests** (about 12–15 scenarios, grouped): one pinned Chromium process, isolated contexts for GM and player, a 1440×900 viewport, reduced motion. They wait on acknowledgements and state versions, never on sleeps.

  Tests assert only on documented surfaces (A5).
- **TST-02** Tests shall be written **blind**, by an agent that sees only this spec and the docs. They are reconciled against the clean app, and every disagreement is resolved by the SRD text or the spec, never by the code. *Why: this is task 21's three-way check, and it stops tests from mirroring bugs in the reference.*
- **TST-03** Tests shall check only observable behaviour. They never check exact wording, orderings the spec leaves undefined, internal ids, CSS values, or timing beyond generous limits.
- **TST-04** The suite shall be split into:
  - F2P tests per bug;
  - sentinels per bug;
  - **14 penalty-bearing regression groups:**
    1. join, identity and reconnect
    2. scenes and maps
    3. tokens and ownership
    4. visibility and fog (including asset authorization)
    5. chat and whispers
    6. dice and determinism
    7. sheet derivations and rolls
    8. damage, healing and death
    9. conditions and advantage
    10. combat tracker
    11. rests and slots
    12. persistence and export (including a server restart)
    13. UI golden path, which also pins the existence of every documented test id
    14. **test-mode parity:** a non-test-mode server set up through import that repeats representative no-dice behaviours from groups 3, 4, 5, 8 and 10

  The pristine visible suite is also run, as a **diagnostic only** that carries no penalty.

  Initiative is sent only as a number in every hidden protocol test (APP-91).
- **TST-05** Regression groups shall include these trap rules:
  - a natural 1 always misses;
  - a crit doubles only the dice;
  - resistance rounds down;
  - temporary HP don't stack;
  - advantage and disadvantage cancel;
  - exhaustion is −2 per level;
  - the concentration DC is between 10 and 30;
  - massive damage kills;
  - PB at levels 4, 5, 16 and 17;
  - half-caster slots at level 1;
  - Stable resets the tallies.
- **TST-06** Validation happens before freeze and is scripted end-to-end. Its results, actual per-phase times and memory peaks go in the metadata. The matrix:
  1. The clean app passes 3/3.
  2. Each bug alone fails exactly its own F2P tests, in both modes (CAT-02).
  3. All 11 together fail every F2P test and nothing else. The TST-10 partition becomes final only when this holds.
  4. Every alternative fix passes.
  5. The visible suite is green on the clean and bugged builds.
  6. The delete-the-feature controls are caught: nudge disabled, drag streaming dropped, and B07's display-only re-sort.
  7. The test-mode special-casing control is caught for B01, B10 and each browser bug (B04, B07, B08). Together these cover one protocol bug, one forced-dice bug and every browser path (§7.4).
  8. **Judge validation:** the six FINDINGS questions are run against three synthetic FINDINGS styles (a terse diff-log, prose, and shotgun) and the votes are recorded.

  About 45–65 full grades in all, roughly 8–12 h of serial machine time, budgeted in the build plan.
- **TST-07** The grader shall rebuild from a pristine scaffold with the frozen lockfile and pre-installed dependencies. It then:
  - copies **only these directory trees** from the agent: `shared/src`, `server/src`, `client/src`, and the client's static assets. Files the agent added inside them are kept;
  - ignores the agent's changes to manifests, the lockfile, configs, build scripts, tests, vendored data and node_modules. Vendored data lives only in root `data/` and never under a copied tree (APP-122), so ignoring it needs no filter;
  - builds, starts the server on a free loopback port, and runs the suite;
  - reports a build or start failure as "did not build";
  - kills the full process tree between phases.
- **TST-08** Browser tests may retry once, and only for an infrastructure error. An assertion failure is final. Protocol tests never retry.
- **TST-09** The scripted grade shall take ≤ 10 min, measured on Josh's machine, not estimated. It covers the build, the protocol tests, the parity group, the browser tests and every F2P's non-test-mode run. It runs one browser at a time, serially.
  - The FINDINGS judge phase runs afterwards as its own step, with its own budget.
  - **Fallback if the measurement overshoots, decided now:**
    1. sample fewer behaviours in the parity group;
    2. trim the non-test-mode browser runs to one F2P per browser bug;
    3. raise the budget to 15 min, with Josh's sign-off at G4.

    F2P and sentinel coverage is never cut to fit the budget.
- **TST-10 Case-level partition.** Before freeze, every hidden case is assigned to exactly one of three places: a bug's F2P set, a bug's sentinel set, or one regression group.
  - A case that fails on any single-bug build or on the all-bugs build can't stay in a regression group or a sentinel set. It is either moved into the F2P set of the bug that breaks it, or narrowed so it no longer exercises the failing path. It is never silently deleted.
  - Each move is recorded with its reason, and a moved case must still pass every alternative fix (CAT-04). The final map is frozen (PKG-04).
  - Blind authors are given this rule up front. Expected first moves:
    - whisper history (B06) out of group 5;
    - drag-stream visibility (B01) and rectangle edges (B11) out of group 4;
    - quick-edit healing (B05) and heal-from-0 tallies (B09) out of group 8;
    - mid-list removal (B03) out of group 10, and typed initiative (B07) out of groups 10 and 13.
  - *Why: TST-06 step 3 and CAT-05 need the regression groups to be independent of every planted bug. Without a written rule, blind authors will naturally test the bug paths inside the groups, and the all-bugs build would then fail groups as well as F2Ps.*

## 11. Constraints
- **Offline at runtime.** The app, workspace and grader make no network calls, and Tailscale is for deployment only. Dependencies and the pinned browser come from the frozen cache.
- **No new dependencies in 22a.** Manifest changes are ignored, so an added package fails the build. The README says so.
- **Web tools and contamination:**
  - WebSearch and WebFetch are denied through `tools.deny` in the run profile for every harness that supports it. Harnesses that can't deny them are reported as such (GRD-03).
  - This is **not** network isolation. Shell and other tool egress stays open, because the agent needs the network for its own model. It is disclosed as an uncontrolled risk and detected by the transcript scan (A8), never claimed as prevented.
- **Licensing:**
  - SRD 5.2.1 CC-BY-4.0 content only, with the exact attribution.
  - "5E-compatible" is the only system reference.
  - Original maps and art, with a declared license.
  - Nothing taken from dataset art.
- **Security:**
  - Cryptographic keys, sent by first-message auth only: never in a URL, cookie or header.
  - Short-lived, single-purpose tickets for assets, uploads and export, re-checked at request time and revoked on removal (APP-13).
  - Origin checks (APP-07).
  - Per-viewer projection of messages and assets.
  - Server-generated file names, upload type and size limits, a message size cap, and a per-connection command-rate cap set well above legitimate use (20 Hz drag plus chat).
  - Text rendered as text.
  - Test mode off by default, loopback-only and secret-gated.
  - Invite regeneration and participant removal.
- **Performance:**
  - 8 clients and 50 tokens per scene.
  - Drag stream ≤ 20 Hz.
  - Move-to-broadcast latency < 100 ms locally.
  - A 60×60 fog layer stays responsive.
  - First load < 3 s on localhost.
  - Scripted grade ≤ 10 min (measured).
- **Determinism.** All game randomness goes through the seeded server dice. No rule or test depends on wall-clock time.
- **Windows:**
  - short workspace roots;
  - retries on atomic renames;
  - the full process tree killed between grader phases;
  - one browser at a time, serial (task 18 memory lesson).
- **Negative assertions — the app shall not include:**
  - accounts or passwords;
  - cloud features or analytics;
  - dynamic lighting;
  - AoE or spell-effect automation;
  - multiclassing;
  - any §3 backlog item;
  - canvas or WebGL rendering libraries;
  - participant keys in URLs, cookies or headers sent to the server;
  - session cookies of any kind;
  - bug hints in code or docs.
- **Size.** 15–25k non-blank lines, no file over 500 lines (APP-142).
